# 04 节点树系统

## 一句话定位

一套「树只描述图、节点自己描述怎么跑」的节点图框架：`NodeTreeData` 只保存层级（`HierarchyInfo`）、节点列表与参数表，边的连接关系由每个 `INodeViewer` 节点自己用 `Add/Remove/GetOutPutList` 维护；编辑器只读写这份数据并轮询节点 `State` 做可视化，因此「运行时执行器 + 节点内部逻辑」可整体外挂，新增节点类型不必改动树结构代码。

> 说明：范围内共 **21 个 .cs**、**2986 行**。全仓搜索显示本工程**没有** `INodeViewer` 的具体实现，执行器与节点逻辑在框架目录之外，「谁驱动遍历」只能按契约推断，相关处标 ⚠。

## 运行流程

1. **建数据**：宿主 MonoBehaviour 持有 `NodeTreeData` 子类字段（实现 `INodeTreeDataOwner`），字段上打 `[OpenNodeView("打开节点树")]`，由 `OpenNodeViewAttributeDrawer<T>`（`NodeTreeSystemWindow.cs:18`）绘制入口按钮。
2. **开窗口**：点按钮 → 补 `Guid` → `InitHierarchInfoList()` → `InitNodesOnEditorWindow()`（对每个节点调 `InitOnEditorWindow(Owner)`）→ 赋静态 `NodeTreeSystemWindow.TreeData` → `OpenWindow()`。
3. **建视图**：`CreateGUI → InitSpeakWindow` 从 UXML 取 `SplitView/TreeView/Inspector/HierarchyPanel`；层级列表选中某项后 `InitNodeViews()` 清空图、逐节点 `new NodeView(data)`、再 `AddEdge()` 按 `GetOutPutList` 还原连线（`NodeTreeSystemWindow.cs:126-127`）。
4. **绑逻辑**：具体节点类型在框架外实现 `INodeViewer`，`Add/Remove/GetOutPutList/TryToGetConditions` 与执行语义都在节点内部；树侧只通过接口调用，不引用任何具体类型。
5. **备参数**：`NodeTreeDataProcessor.Init(owner.GetParameterList())` 逐条 `DeepCopy`（`NodeTreeDataProcessor.cs:140`），运行时改值不污染资产。
6. **逐节点执行**：取后继 → `GetOutPutList(out var list)`；分支判定 → `TryToGetConditions` 给出 `List<Condition>`，再由 `RegisterCondition` 求值；串/并联由各节点端口 `Port.Capacity`（Single/Multi）表达。⚠ 遍历循环本身不在本目录内，调用方式无法确认。
7. **逐帧镜像**：`OnInspectorUpdate → TreeView.OnGUI → NodeView.UpdateNodeView`（`TreeView.cs:115`）轮询 `NodeData.State`，执行中换色并给入边挂流动点。
8. **结束/落盘**：执行器把 `State` 置为 `Finished/Failed/Successful/Stop`；窗口 `OnDestroy → Save()` 在非播放模式写回 `WindowData` 并保存场景（`NodeTreeSystemWindow.cs:236-244`），进出播放模式时窗口被关闭。

## 关键机制详解

### 解耦（核心）：树只依赖 `INodeViewer`，不依赖任何节点类型

只有四个依赖面，全部是抽象，因此「加一种节点逻辑」不会触碰树结构代码：

1. **节点只是接口**：`INodeViewer.cs:32` 定义 `public interface INodeViewer`，树数据用泛型约束吃掉具体类型——`HierarchyInfo<T,O,H>` 里 `public List<T> HierarchyNodes` 且 `where T : INodeViewer<T,O>`（`NodeTreeData.cs:22-25`）。`NodeView` 也只持有 `public INodeViewer NodeData;`（`NodeView.cs:13`）。
2. **边由节点自己存，树里没有边表**：连线时 `NodeTreeSystemWindowUtility.ConnectNode` 仅转发给节点——
   ```csharp
   public static void ConnectNode(this Edge edge) {
       NodeView input = edge.input.node as NodeView;
       NodeView output = edge.output.node as NodeView;
       output?.AddChild(input);   // → NodeData.Add(nodeView.NodeData)
   }
   ```
   于是「图长什么样」由节点实现决定，树的增删只需 `HierarchyInfo.AddNode/RemoveNode`。复制粘贴时同样只面向接口：`SerializationUtility.SerializeValue<List<INodeViewer>>` 二进制往返（`NodeExtension.cs:15-16`），Odin 多态序列化保证不关心具体类型。
3. **节点自己汇报后继与条件**：`GetOutPutList`、`TryToGetConditions`、`Sort`（返回 true 时 `NodeView` 会 `OutputPort.DisconnectAll(); AddEdge();` 重连，`NodeView.cs:66-70`）。顺序、选择、并行等语义因此完全由节点实现决定。
4. **类型只在"创建菜单"和"面板"处被反射发现**：`Activator.CreateInstance((Type)searchTreeEntry.userData) as INodeViewer`（`TreeView.cs:221`），类型来自 `TreeData.GetNodeType().GetDerivedClasses()` + `NodeLabelAttribute`；面板用 `[ShowNode(typeof(X))]` 匹配后同样反射实例化（`Inspector.cs:76-90`）。两处都是扫描 + 特性。

结论：解耦手段是**接口契约 + 泛型约束 + 特性驱动的反射发现 + 图结构数据内聚在节点自身**，未使用委托，执行入口（遍历）也不在框架里。

> **执行权归属（设计如此，不是缺口）**：`NodeTreeDataProcessor` 虽然叫 Processor、也继承 `SerializedMonoBehaviour`，但它的职责是**参数容器与条件求值**（`RegisterCondition` / `FindParameter` / `SetFloat|SetInt|SetBool|SetTrigger`），不负责遍历节点。
> 这套系统的定位就是「只提供链路」：树结构、条件求值、执行态可视化由框架给，**执行器不做**——挂载了对应接口的节点对象自己关心这些节点该如何执行。所以加一种节点逻辑既不用改树、也不用改编辑器，代价是执行逻辑分散在各节点实现里。具体节点与驱动逻辑在业务工程侧实现，不在 `MyFrame` 目录内，属预期情况。

### 端口是数据：串/并联由 `PortInfo` 描述

`PortInfo` 只存 `orientation/direction/capacity/type`（`INodeViewer.cs:15-29`），`NodeView.InitNode` 据此泛型建端口：`PortView.CreatePort<Edge>(inputPortInfo)`；`GetOutputPortInfo` 返回 false 即终点节点（无输出端口）。故串联/并联只是节点类型的数据属性，`NodeView` 无需分支。兼容性由 `TreeView.GetCompatiblePorts` 用 `startPort.portType.IsAssignableFrom(节点类型)` + 方向相反来限制。

### 参数与条件：Guid 引用 + 按类型分派

宿主提供 `List<ParameterForTree>`，每个参数带 `Guid`；`Condition` 只存 `ParameterID`（Guid 字符串）而不引用字段，故删改参数名不影响条件。求值集中在 `RegisterCondition`：按 `Parameter.Type` 分派到 `Bool/Float/Int/TriggerConditionCheck`，`Trigger` 读一次即消费——`if(!isCheck) parameter.SetValue(false);`（`NodeTreeDataProcessor.cs:197-205`）。

### 编辑器如何按节点类型动态生成面板

`Inspector.Init` 里 `_inspectorItemTypes = typeof(InspectorItemBase).GetDerivedClasses()` 缓存所有面板类型；`UpdateInspector` 对每个选中 `NodeView` 找 `ShowNodeAttribute.NodeType == n.NodeData.GetType()` 的面板类型，反射实例化后 `Init(InspectorBar, n.NodeData)` 再 `CreateInspectorGUI()`。基类泛型版 `InspectorItemBase<T>` 已包办标题输入框绑定 `NodeName` 与载入 `InspectorItemRoot.uxml`，子类只写业务字段。若 `TryToGetConditions` 返回 true，面板下方再叠一个 `ConditionListView`。

### 执行态外置：编辑器只读 `State`

`NodeState { Waiting, Executing, Finished, Failed, Stop, Successful }` 是节点字段，框架内没有任何地方给它赋值，只有读：`if (Application.isPlaying && NodeData.State == NodeState.Executing) ChangeBarColor(ExcutingNodeColor);`（`NodeView.cs:53-60`），并据此 `OnStartMovePoint/OnStopMovePoint`。这证明执行由外部决定，编辑器只是观察者。

### 自动布局：Walker 非分层 tidy tree

`NodeAutoLayouter` 是 non-layered tidy tree（Walker）实现。`FirstWalk` 自底向上算 `prelim` 与子树偏移 `mod`，`secondWalk` 自顶向下累加 `mod` 得绝对 `x`；相邻子树由 `Seperate` 比较左右轮廓，用 `tl/tr` 线程指针跳转、`IYL` 链表按 `bottom` 高度裁剪待比兄弟；`DistributeExtra + addChildSpacing` 把间距均摊给中间子树（`shift/change`），`GetPos` 按 `CalculateMode` 旋转/镜像。适配器 `RNG_LayoutNodeConvertor` 从 `RootNodeView` 沿 `OutputPort.connections` 递归建 `TreeNode`（尺寸硬编码 250×120、`SiblingDistance=100`，`TreeDistance` 声明未用），算完逐节点 `SetPosition` 回写。

## 对外 API 与扩展点

**新增一种节点类型**：写 `class XxxNode : INodeViewer<XxxNode, XxxOwner>`，实现 `Position/NodeName/State/GUID/TreeID`、`Add/Remove/GetOutPutList`、`GetInputPortInfo/GetOutputPortInfo`、`Sort`、`TryToGetConditions`、`ChangeCurrentList`、`Init/InitOnEditorWindow/DeepCopy`，加 `[NodeLabel("分组/菜单名", Label="标题")]`；需分支则返回 `Condition` 列表。无需改 `TreeView/NodeView/NodeTreeData`。

**新增一种节点逻辑（不改树）**：只改该节点的 `GetOutPutList` 与 `State` 推进方式（顺序=返回下一个；并行=返回多个 + 多出边端口；选择=按 `RegisterCondition` 过滤后继）；树结构与编辑器零改动。

**新增面板**：`class XxxInspectorItem : InspectorItemBase<XxxNode>` + `[ShowNode(typeof(XxxNode))]`，实现 `CreateInspectorGUI/UpdateInspectorGUI`。

**新增一种树**：继承 `NodeTreeData<T,H,O,D>` 与 `HierarchyInfo<T,O,H>`，宿主字段打 `[OpenNodeView("...")]`；颜色表把 `BaseType` 指到节点根类型后点「创建默认节点颜色」即可批量补条目。

## 与其他模块的耦合

- **MyFrame 扩展**：`GetDerivedClasses/GetTypeUnderTheGenericType`（`Script/Extension/FrameExtension.cs:93`）扫描全 `AppDomain`，是菜单与面板自动发现的基础；`IDeepCopy<T>` 串起树/节点/参数深拷贝。
- **Odin Inspector**：`SerializedMonoBehaviour`、`SerializedScriptableObject`、`OdinSerialize`、`OdinAttributeDrawer`（按钮抽屉）、`Sirenix.Serialization`（复制粘贴）。
- **UnityEditor**：`UnityEditor.Experimental.GraphView`（`PortInfo` 直接用 `Port.Capacity`）、UIElements/UXML/USS，资源路径硬编码为 `Assets/MyFrame/NodeSystemTree/Editor/Resources/...`。
- **业务残留**：`SpeakSystemWindowSetting` 是对话专用配色并 `Resources.Load("WindowSetting")`；命名空间双轨——数据层在**全局命名空间**，编辑器层并存 `NodeSystemTree.Editor.SpeakTreeView` 与 `SpeakSystemTree.Editor.SpeakTreeView`（`EdgeView.cs`）两套根。
- **宿主/具体节点**：只依赖 `INodeTreeDataOwner`、`INodeViewer` 两个契约，本工程未提供实现。⚠ 具体节点与执行器是否在另一工程/分支待确认。

## 设计亮点与可改进点

**亮点**：① 解耦靠契约而非事件总线，改造面极轻；② 图结构内聚在节点内，编辑器只是投影；③ 端口数据化，串/并联无需 switch；④ Odin 多态序列化白送复制粘贴与深拷贝；⑤ 颜色表扫派生类自动补全；⑥ tidy-tree 布局让父节点居中于子节点。

**可改进点**：
- 数据层不"运行时干净"：`NodeTreeData.cs`/`INodeViewer.cs` 在全局命名空间，`PortInfo` 依赖 `UnityEditor.Experimental.GraphView`，`NodeTreeDataProcessor.cs` 还 `using UnityEditor`（第 6 行）——进 runtime 程序集会编译失败。
- 全局静态单例：`NodeTreeSystemWindow.Window/TreeData` 被各视图到处直接取用，多窗口/多树并存不可行，也不便测试。
- 缺少统一删除入口：`TreeView.RemoveFromSelection` 与 `OnGraphViewChanged` 的 `elementsToRemove` 都会调 `RemoveNode`，重复维护易漏。
- 条件求值不健壮：`FloatConditionCheck` 只写 `Greater/Less` 两个分支（Int 有三个），非穷尽 switch 在其余 `ContrastType` 下会抛 `SwitchExpressionException`。
- `Inspector.UpdateInspector` 判空写成 `if (n == null && n.NodeData == null) return;`，应为 `||`，`n` 为 null 时会 NRE。
- `EdgeView` 的流动点动画整体被注释（`UniTask` 循环），只创建 4 个 `MovePoint` 却不移动，执行中反馈失效。
- `NodeTreeDataManager` 仅一个 `Dictionary<string,GameObject>` 且全仓无引用，存在意义 ⚠ 待确认。
- 参数/条件三类列表视图的字段工厂是重复样板（每加一种 `ParameterType` 要改 3 处 switch），可抽统一字段构造器。
