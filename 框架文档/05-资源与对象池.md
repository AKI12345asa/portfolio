# 05 资源管理与对象池

## 一句话定位

`ResSystem` 是架在 **Addressables** 上的静态资源门面，把「按地址取资源/实例化预制体」和「先查对象池、池空再实例化」合并成一次调用；`PoolSystem` 是它的下层容器，用同一套字符串 key 维护两套池——普通 class 对象池 `ObjectPoolModule` 与 GameObject 池 `GameObjectPoolModule`。框架**没有显式引用计数表**，计数由 Addressables 内部承担，`autoRelease` 只把「实例被销毁」翻译成「释放」。

> 行数以实际读取为准（`ResSystem.cs` 实为 240 行，与任务书的 226 行有出入）。`ResSystem` 未声明命名空间（位于全局命名空间），靠 `using MyFrame;` 访问 `PoolSystem`；`PoolSystem` 及其模块、数据类均在 `MyFrame` 下。

## 运行流程

1. **初始化**：`MyFrameRoot.Awake` → `InitSystems()`（`[DefaultExecutionOrder(-20)]`）按 SaveSystem → **PoolSystem** → EventSystem → … 顺序。`PoolSystem.Init()` 只做三件事：new 两个 Module、取/建 `PoolRoot` 并挂到 `FrameRootTransform`、`GameObjectPoolModule.Init(poolRootTransform)`。**此时一个池都没有建**；`ResSystem` 无 `Init`，首次调用即可用。
2. **建池（可选）**：业务显式调用 `InitGameObjectPool` / `InitObjectPool`；或走 `ResSystem.InitGameObjectPoolForKeyName`，用 `Addressables.InstantiateAsync(...).WaitForCompletion()` 预生成 `defaultQuantity` 个实例再交给池。
3. **加载/取用**：以 `ResSystem.InstantiateGameObject(assetName, parent)` 为例——先 `PoolSystem.GetGameObject(poolName ?? assetName, parent)`；命中直接返回池对象，未命中执行 `Addressables.InstantiateAsync(assetName, parent).WaitForCompletion()`，按 `autoRelease` 挂释放监听，再改名。
4. **回收**：`PoolSystem.PushGameObject(go)`（或 `go.GameObjectPushPool()`）→ 先 `PushAction` → 超容量则 `Destroy` → 否则挂回 `poolRoot`、`SetActive(false)`、改名、入队。
5. **卸载**：`ResSystem.UnloadInstance(go)` → `Addressables.ReleaseInstance`（连带销毁实例）；业务若直接 `Destroy`，由第 3 步挂的监听触发同一次释放。资源用 `UnloadAsset` / `UnLoadAssetsHandle` 释放。

## 关键机制详解

### 1. autoRelease：借 OnDestroy 事件实现「销毁即释放」

各实例化 API 的 `autoRelease` 默认 `true`，实例化后立刻给实例挂监听：

```csharp
go.transform.OnReleaseAddressableAsset(AutomaticReleaseAssetAction);
// FrameEventExtend → AddEventListener(com, EventType.OnReleaseAddressableAsset, action)
// EventListener.OnDestroy → TriggerAction(EventType.OnReleaseAddressableAsset, gameObject)
private static void AutomaticReleaseAssetAction(GameObject obj)
    => Addressables.ReleaseInstance(obj);
```

所以调用方不必持有 handle：业务 `Destroy` 掉实例就等于释放了 Addressables 引用。代价是实例上多一条事件监听，且「销毁」与「释放」被强绑定——想把实例留在池里长期复用，就必须传 `autoRelease: false`。

### 2. 两套池的分工与 key 约定

key 一律是**字符串**，没有类型 key。class 池的默认 key 是 `typeof(T).FullName`（无 name 的重载），GameObject 池的默认 key 是 `{prefab.name}Pool` 或 `{assetName}_Pool`。注意 `PushObject(obj)` 按 `obj.GetType().FullName` 找池，`GetObject<T>()` 按 `typeof(T).FullName` 找池：以基类取、以子类还就会落进两个池，对象回不去。

### 3. 容量、扩容与复用重置

- `MaxCapacity = -1` 表示不限。class 池超容量时**直接丢弃**（不入队、不销毁、无日志）；GameObject 池超容量时 `Destroy` 实例并返回 `false`，且是先执行 `PushAction` 再判容量，class 池则相反。
- **没有扩容策略，也没有自动预热**：池空时 class 池用 `CreateFunc` 或无参构造反射新建；GameObject 池直接返回 `null`，由上层（`ResSystem`）决定要不要 Addressables 实例化。
- 复用重置只做三件事：`SetParent`、`SetActive(true)`、改回 `objectName` 去掉 `(Clone)`；出池且 `parent == null` 时还会 `MoveGameObjectToScene` 回当前活动场景。粒子、动画、计时器等内部状态没有统一钩子，只能靠 `getAction`/`pushAction` 或业务自行重置（`EffectController.Init` 手动 `Stop`/`Clear`/`Play` 即是此因）。

### 4. 池根节点与池对象的自复用

`PoolSystem.Init` 建 `MyFrameRoot/PoolRoot`；每个池的根节点由 `GameObjectPoolData.Init` 建成 PoolRoot 的子物体并命名为 `poolName`。`Destroy()` 不销毁池根，而是 `PushGameObject("PoolDataRoot", poolRoot.gameObject)` 加 `PushObject(this)` 归还——池根与 `GameObjectPoolData` 本身也进池复用。同理 `CreatePoolData`/`CreateGameObjectPoolData` 都是先 `PoolSystem.GetObject<...>()` 再 `?? new`。

### 5. 异常处理现状

只用 `Debug.LogError` 挡明显误用：容量超上限、预制体为空、空对象入池、找不到池名。无 `try/catch`；异步回调不校验 `handle.Status`，失败时把 `handle.Result`（null）交给 callback；同步路径用 `WaitForCompletion()` 阻塞主线程。`poolName` 传 `null` 则会因 `Dictionary.TryGetValue(null, …)` 抛 `ArgumentNullException`（`InstantiateGameObjectAsync(Transform, …)` 未判空）。

## 对外 API 与扩展点

```csharp
// 1) 同步：先查池，未命中走 Addressables 实例化并挂 autoRelease
var go = ResSystem.InstantiateGameObject("Prefabs/Effect/Hit", effectRoot);

// 2) 异步：池命中直接回调，否则等 Addressables 完成
ResSystem.InstantiateGameObjectAsync("Prefabs/Effect/Hit", obj => { /* 使用 */ }, effectRoot);

// 3) 只要资源不要实例
var clip = ResSystem.LoadAsset<AudioClip>("Audio/BGM/Main");
ResSystem.UnloadAsset(clip);

// 4) 从 class 池取一个再还回去
PoolSystem.InitObjectPool("HitInfoPool", () => new HitInfo(), maxCapacity: 20, defaultQuantity: 10);
var info = PoolSystem.GetObject<HitInfo>("HitInfoPool");
PoolSystem.PushObject(info, "HitInfoPool");
```

- `getAction`/`pushAction` 是唯一的内置生命周期钩子，建池时传入，可用于重置与埋点；`RemovePool` 系列可整池摘除（GameObject 池会 `Destroy` 实例）。
- Module 可以脱离 `PoolSystem` 独立 `new`：`AudioModule` 就是 `new GameObjectPoolModule()` + 自己的 `poolRoot`，不受全局池影响——目前唯一的「每系统独立池」范式。
- `FrameExtension` 提供 `GameObjectPushPool` / `ObjectPushPool` 回收语法糖。
- `PoolSystem` 并未透出 `ObjectPoolModule.ClearPool`，该能力目前只有 Module 层可达。

## 与其他模块的耦合

- **UI**：`UISystem.PreInitWindows` 与 `ShowWindow` 用 `ResSystem.InstantiateGameObject<UIWindowBase>(windowData.assetPath, layout.root, objName: key)`，`autoRelease` 取默认 `true`；`Close` 时若 `ifCache == false` 走 `ResSystem.UnloadInstance(window.gameObject)`，代码注释明确「不需要再 Destroy」。由于未传 `poolName`，池 key 等于 `assetPath`，而框架从未为该 key 建池，实际恒走 Addressables。
- **战斗特效**：`Skill_Player`、`GenerateEffectEventProcessor`、`SWSActionModuleBehaviour` 用 `PoolSystem.GetGameObject(prefab)`（prefab 重载，池空时用 `GameObject.Instantiate` 兜底，**不经 Addressables**）；`EffectController` 在 `DestroyTime` 到期后 `PoolSystem.PushGameObject(gameObject)`，按 `{name}Pool` 归还——两端依赖 `{prefab.name}Pool` 这条命名约定，改名就会串池。
- **音频**：`AudioModule` 自建 `"AudioPlayPool"` 播放池（`GameObjectPoolModule` 独立实例），`ResSystem` 只负责 `clip` 的 `LoadAsset` 与 `UnloadAsset`（`autoReleaseClip`）。
- 另有 `MonoSystem`（`List<Coroutine>` 池）与 `BehaviourExecutor`（`BehaviourHandler` 池）是 class 池的主要使用者，均靠 `getAction`/`pushAction` 里的 `Clear()` 重置。

## 设计亮点与可改进点

**亮点**

1. 门面—模块—数据三层清晰，Module 可独立实例化（音频池即例证），池实现与全局入口解耦。
2. 双池都做「自身复用」：整池销毁时池根与 `PoolData` 回流，减少反复 new。
3. `autoRelease` 把 Addressables handle 生命周期藏进事件系统，业务侧一行取、一行还，漏释放风险低。
4. 统一的字符串 key 约定配合扩展方法语法糖，接入成本低。

**可改进点**

1. `GameObjectPoolModule.InitGameObjectPool(..., GameObject[] gameObjects, maxCapacity)` 中 `Math.Min(poolData.PoolQueue.Count - maxCapacity, gameObjects.Length)` 恒为负（此时必有 `Count < maxCapacity`），`maxCapacity != -1` 时预填充分支永不执行；且 `ResSystem` 的预填充实例直接由 `Addressables.InstantiateAsync` 产生，没有挂 `autoRelease` 监听。
2. `ResSystem.InitGameObjectPoolForKeyName` 在不传 `assetName` 或 `defaultQuantity <= 0` 时调用的是无 prefab 的重载，模块内「预制体不能为空」会直接 return——该参数组合下建不出池。
3. `ObjectPoolModule.InitPoolData<T>(int maxCapacity, …)` 把 `pushAction` 传进了 `getAction` 形参位置（实参错位），该重载目前无人调用，属潜伏缺陷。
4. key 约定不统一：`InitGameObjectPoolForAssetName` 建 `{assetName}_Pool`，而 `InstantiateGameObject` 不传 `poolName` 时查 `assetName`，两者对不上，预填充会白做。⚠ 待确认：是否存在按裸 `assetName` 显式建池的业务代码未在本次检索范围内覆盖。
5. 无引用计数表，大量 `WaitForCompletion()` 同步阻塞；异步分支不校验 `handle.Status`，失败即把 null 交给业务。
6. 缺 `IPoolable`/`OnSpawn`/`OnDespawn` 接口，重置只能靠委托；`ObjectPoolModule` 无 `Destroy/Dispose`，`RemoveObjectPool` 只把池从字典摘除、池内对象不清理（与 `GameObjectPoolModule.RemovePool` 会销毁实例不一致）；整个框架也没有统一的 `Shutdown`。
