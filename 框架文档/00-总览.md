# 00 MyFrame 框架总览

> 本目录是对 `E:\GameMake\Demo\Assets\MyFrame` 的全量源码通读结果。
> 206 个 C# 文件、约 **24,000 行**代码，按 9 个模块拆成 8 份文档，每份都标注了文件与行号，方便对照源码阅读。

## 这是什么

MyFrame 是一套**面向动作游戏的自研 Unity 客户端框架**，不含任何业务逻辑，通过 `MyFrame.asmdef` 作为独立程序集供业务层引用。它的重心不在"通用工具"，而在四件难做对的事：

1. **动画**——绕过 Animator 状态机，用 Playable API 手搭混合树；
2. **战斗**——以"帧时间轴 + 事件 + 可注册处理器"描述技能，而非写死在代码里；
3. **AI**——GOAP 做决策，与表现状态机并行；
4. **内容生产**——技能编辑器、GOAP 编辑器、节点树编辑器三套可视化工具。

框架本身不规定玩法，只提供"数据怎么描述、表现怎么挂接、每帧谁来驱动"这三层约定。

## 启动链路：MyFrameRoot

`Script\MyFrameRoot.cs`，`[DefaultExecutionOrder(-20)]`，`Awake` 里自建单例并 `DontDestroyOnLoad`：

```
Awake
 ├─ Instance = this（重复实例直接 Destroy）
 ├─ DontDestroyOnLoad
 └─ InitSystems()
      SaveSystem.Init()    ← 存档必须先起（其它系统可能读设置）
      PoolSystem.Init()
      EventSystem.Init()
      UISystem.Init()
      MonoSystem.Init()
      AudioSystem.Init()
      TimeSystem.Init()
```

外加一个**只在编辑器下**的引导器：`[InitializeOnLoad]` + `sceneOpened` / `hierarchyChanged` / `playModeStateChanged` 三个回调，在非运行态反射扫描 `UIWindowDataAttribute` 生成窗口表（`InitSetting → InitWindowDataInConfig`），并在进出播放模式时重建。

> ⚠ **一个需要留意的点**：`InitWindowDataInConfig()` 的唯一调用点是 `InitSetting()`，而 `InitSetting()` 只在编辑器路径被调用（`MyFrameRoot.cs:205`）。运行时 `Awake` **不会**重新扫描特性，窗口表来自 `MyFrameSetting` 资产中已序列化的 `UIWindowDataDic`。也就是说：新增一个窗口类后，必须在编辑器里让 `FrameWindow` 把它写回 setting 资产并保存，否则打包运行后 `ShowWindow` 会抛 `当前的Window数据没有被注册过`。这一点建议加个打包前校验。

## 四条贯穿全框架的设计取向

**1. 数据与表现分离。**
`SkillClip` 只记录"第几帧发生什么"，具体怎么做交给 Processor；`NodeTreeData` 只描述图，节点怎么跑由 `INodeViewer` 实现；`SkillBehaviourBase` 可 `DeepCopy` 成原型，运行时实例与资产解耦。这条线是框架最一致的地方。

**2. 特性驱动的"扫描—注册"。**
`UIWindowDataAttribute`、`CameraEventAttribute`、`[GOAPAction]`、`[NodeLabel]`、`[ShowNode]` 都不是装饰，而是注册表：`FrameUtility.GetTypesByAttribute` 遍历 `AppDomain` 全程序集建表。**加一个类就等于加一个功能，不用改任何注册代码**——代价是每次都要付反射扫描的成本（目前只在初始化/编辑器阶段扫描，符合预期）。

**3. 帧驱动集中化。**
`MonoSystem` 用一个 `static event Action updateAction` 收拢全框架的 `Update`：动画节点的相位同步（`AddUpdate(SyncPhase)`）、协程托管都挂在这里；`Skill_Player` 则自己持有 `Update` 做帧推进。框架没有统一的 Tick 调度器，是"两个驱动源并存"的状态。

**4. 池化与零分配倾向。**
`PoolSystem` 两套池（普通 class 池 / GameObject 池）、`GOAPObjectPool`、`MonoSystem` 的协程列表回池、检测用 `Physics.Overlap*NonAlloc`、事件条目池化——GC 敏感的意识贯穿多处，尽管落地程度不一。

## 一次技能播放的端到端链路

这是最能体现九模块协作的一条路径，链路在 Demo 里有真实实现：

```
① GOAP 决策
   GOAPAgent 选目标 → 逆向规划 → 计划里出现 [GOAPAction("技能播放")]
   Demo_PlaySkillAction.BeforePlanningUpdateEvent
       └─ 向 SkillBehaviour 要 Priority / Cost（技能自己决定值不值得放）

② 释放
   Demo_PlaySkillAction.OnStart
       └─ EnemySkillBrain.ReleaseSkill(skillConfig)

③ 播放
   SkillBrain → Skill_Player.PlaySkillClip(clip)
       └─ Update 里按帧率推进：_playTotalTime += timeScaleContainer.GetDeltaTime()
          逐帧 while 推进，一帧可补多帧

④ 帧事件分发（帧内固定顺序）
   Custom → Animation → Audio → Effect → AttackDetection
       ├─ 动画轨：Animation_Controller 过渡到目标节点（双端口权重插值）
       ├─ 检测轨：SkillAttackDetectionTool 盒/球/扇 Overlap → IHitTarget.BeHit
       └─ 相机轨：CameraEventProcessor 四段生命周期（Start/Tick/End/Reset）

⑤ 命中表现
   DetectionEventProcessor 注册表（typeof(T) 为键）
       ├─ AttackEventProcessor    → 结算伤害
       ├─ AudioEventProcessor     → AudioSystem.PlayOneShot
       ├─ GenerateEffectEventProcessor → PoolSystem 取特效
       ├─ StutterFrameProcessor   → TimeSystem 顿帧
       └─ ImpulseEventProcessor   → 攻击方/受击方双向震屏
```

**解耦点**：`Skill_Player` 不认识任何表现；表现方以"处理器"形式注册进字典，未注册就静默跳过（Demo 里玩家注册 5 个、敌人只注册 4 个，正是这个机制的直接证据）。

## 已知短板汇总

通读时确认的可改进点（各文档内有详细定位与行号）：

| 模块 | 问题 | 影响 |
| --- | --- | --- |
| 战斗 | `TickSkillEffectEvent` 只有一个 `_currentEffect` 字段，同时存在多个特效事件时会互相串位 | 多特效技能表现错乱 |
| 战斗 | 形状检测的 `ForEach` lambda 里用了 `return`，本帧剩余碰撞体被跳过 | 同时命中多个目标时漏判 |
| 战斗 | `ReleaseAgain` 直接索引字典可能抛异常；`AutoDestruct` 会把 `Instantiate` 兜底的临时实例也回池 | 偶发异常 / 池污染 |
| 资源池 | `GameObjectPoolModule.cs:91` 的 `Math.Min(Count - maxCapacity, …)` 恒为负，预填充分支永不执行 | 池不会被预热 |
| 资源池 | `ObjectPoolModule.cs:118` 把 `pushAction` 传进了 `getAction` 形参 | 回收/取出时回调错位 |
| 资源池 | `ResSystem.InitGameObjectPoolForKeyName` 不传 assetName 时必然报错返回 | 该重载实际不可用 |
| 节点树 | 运行时执行器未落地，全工程无 `INodeViewer` 实现，Demo 也未使用 | 目前只有编辑期价值 |
| 事件 | `AddTypeEventListener<T>` 用 `nameof(T)` 做 key，所有泛型类型事件会挤在同一个 key 上 | 类型事件不可用（⚠ 待确认） |
| UI | `ShowWindow<T>` 用 `typeof(T).Name` 查表，而特性注册时 Type 重载用 `FullName`，两者对不上 | 按类型开窗会查不到 |
| UI | 运行时窗口表依赖编辑器写回 setting 资产（见上文启动链路） | 打包后新窗口可能注册失败 |
| GOAP | 框架内**没有感知层**，世界状态靠 `IGOAPOwner` 每帧外部写回 | 框架与"谁提供感知"强绑定在业务侧 |
| MonoSystem | `AddUpdate(this object obj, Action)` 扩展方法**忽略了接收者**，只往全局多播里加，无法按对象批量退订 | 对象销毁时漏写 `RemoveUpdate` 就会留下悬挂委托（Demo 里已出现） |
| GOAP | 规划无环检测、同优先级动作可能被静默丢弃、无累计代价、失败每帧刷日志 | 复杂配置下行为不可预期 |
| 全局 | 多处 `using UnityEditor` 没包 `#if UNITY_EDITOR`（GOAP 2 处、`MyFrameSetting`、`FrameUtility`、`KeyConfigs`），而 `MyFrame.asmdef` 是全平台 | **出包编译风险**（建议优先核实） |
| 音频 | `MonoSystem.Stop_Coroutine` 缺单参重载，`AudioModule.StopBGAudio` 把协程当字典 key 传 | 背景音乐停不掉（静默失效） |
| 输入 | `InputManager` 不在 `InitSystems` 里，`ICanInputComponent` 全工程无实现者 | 输入层实际未接入 |
| 状态机 | `BehaviourExecutor` 抢占失败/被抢占的 handler 既不 `End` 也不 `Destroy`；构造函数每 new 一次就重复 `InitObjectPool` 同名池 | 池泄漏 / 重复建池 |
| 时间 | `TimeSystem` 顿帧两个字典命名与内容相反；`RegisterAsTimeOwner` 用 `TryAdd`，重复注册后容器与字典错位 | 顿帧行为不符合直觉 |
| 动画 | `Animation\` 整目录无命名空间；`GradientBand` 全工程无调用点；`PushPool(isForced)` 基类忽略参数 | 命名冲突风险 / 死代码 |
| 存档 | 无加密、无校验、无版本迁移；缓存只写不读；全部主线程同步 IO | 存档兼容性与卡顿风险 |
| 技能编辑器 | 缩放下全量重建条目；反射 `UnityEditor.AudioUtil` | 大技能卡顿 / 版本兼容风险 |
