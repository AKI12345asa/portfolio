# 07 存档系统

## 一句话定位

`MyFrame` 的存档层：以「存档槽目录 + 数据块文件」为存储模型，用 `SaveSystem` 静态 API 与 `DataManager<G,S>` 泛型基类，在 **Binary（BinaryFormatter）/ Json（JsonUtility）** 两条通道上读写玩家存档与全局设置，并用 `Serialized_Dic`、`Serialized_Vector`、`Serialized_Color` 三个包装类型抹平序列化差异。

## 核心类型

| 类型 | 基类/接口 | 职责 | 关键方法 |
| --- | --- | --- | --- |
| `SaveSystem` | `static class` | 存档系统门面，全部 API 为静态 | `Init`、`CreateSaveItem`、`SaveObject`、`LoadObject`、`LoadSetting`、`SaveSetting`、`GetDataManager<M>` |
| `SaveItem` | `[Serializable]` 普通类 | 一个存档槽的元数据：`saveID` + 最后保存时间 | `UpdateTime`、`LastSaveTime`（懒解析 `lastSaveTimeString`） |
| `SaveSystemData`（私有） | `[Serializable]` 内部类 | 存档索引：`currID`、`saveItemList`、`testItem`，整体存成 `SaveData/SaveSystemData` 单文件 | 仅作字段容器 |
| `GameDataContainer` | 抽象类 | 玩家存档数据块标记，禁止直接实例化 | 静态 `Create<T>(params object[])` → `Initialize` |
| `GameDataContainer<T>` | 继承 `GameDataContainer` | 自引用泛型约束，让 `DataManager<G,S>` 能拿到具体类型 | 无 |
| `SettingDataContainer` | 抽象类 | 设置数据块标记，全局唯一、与存档槽无关 | `Initialize()`（抽象，**框架路径未调用**） |
| `SettingDataContainer<T>` | 继承 `SettingDataContainer` | 同上，泛型自约束 | 无 |
| `DataManager` | 抽象类 | `DataManager` 的公共基类，供 `GetDataManager<M>()` 的 `new()` 约束使用 | `Initialize()` |
| `DataManager<G,S>` | `DataManager` | 业务侧持有者：加载设置、创建/读取/保存当前存档、抛事件 | `CreateArchive`、`LoadArchive`、`SaveGameDataIntoArchive`、`RegisterOnGameDataSave` |
| `Serialized_Dic<K,V>` | `ISerializationCallbackReceiver` | 让 `Dictionary` 能走 Unity 序列化/JsonUtility | `OnBeforeSerialize`、`OnAfterDeserialize` |
| `Serialized_Vector3/2`、`Serialized_Color` | `struct` | Unity 值类型的纯 float 镜像，双向 `implicit operator` | `ConverToVector3` 等扩展 |
| `SaveSystemType`（枚举在 `Config/MyFrameSetting.cs`） | `enum` | 序列化通道开关：`Binary`（默认）/`Json` | 由 `MyFrameSetting` 资产提供 |

## 运行流程

1. **初始化**：`MyFrameRoot.Awake` → `InitSystems()` 第一件事调用 `SaveSystem.Init()`。`Init` 拼出 `Application.persistentDataPath` 下的 `SaveData` 与 `Setting` 两条路径，`CheckAndCreateDir()` 建目录，再由 `InitSaveSystemData()` 读 `SaveData/SaveSystemData`；读不到（首次运行）就 `new SaveSystemData()` 并立即回写。
2. **建槽**：业务调用 `SaveSystem.CreateSaveItem(id)`（已存在则先删），得到 `SaveItem` 并刷新索引文件；`id == -1` 走内置 `testItem` 测试槽。
3. **写存档**：`SaveGameDataIntoArchive(index)` 触发 `OnGameDataSave`，再 `SaveObject(GameData, index)`（文件名默认取 `data.GetType().Name`）；后者校验槽存在 → 建 `SaveData/{id}` 目录 → 按 `SaveSystemType` 分流写盘 → 刷新槽时间戳 → 重写整份 `SaveSystemData` → 写入 `cacheDic`。
4. **读存档**：`LoadObject<T>(fileName, saveID, ifUseCache)` 先查 `cacheDic`；未命中则校验槽与目录，`LoadFile<T>` 从 `SaveData/{id}/{fileName}` 反序列化。`LoadArchive` 把结果写入 `GameData` 并触发 `OnGameDataLoaded`。
5. **版本处理**：**没有**。8 个文件无版本号字段、无迁移钩子、无格式头；Binary 通道靠 `BinaryFormatter` 记录类型元数据，Json 通道靠字段名。因此只有「读失败返回 null」这一种事实上的降级路径。

## 关键机制详解

### 1. 双通道序列化，由配置资产开关

```csharp
private static void SaveFile(object saveObject, string path)
{
    switch (MyFrameRoot.Setting.SaveSystemType)
    {
        case SaveSystemType.Binary:
            IOTool.SaveFile(saveObject, path);          // BinaryFormatter
            break;
        case SaveSystemType.Json:
            string jsonData = JsonUtility.ToJson(saveObject);
            IOTool.SaveJson(jsonData, path);
            break;
    }
}
```

开关来自 `MyFrameSetting.SaveSystemType`，编辑器窗口 `FrameWindow` 用下拉框写入。两条通道**无文件头标识**，运行时切换模式后旧文件即读不出来。

### 2. `Serialized_Dic`：一份数据同时喂给两套序列化

```csharp
public void OnBeforeSerialize()          // Unity 与 [OnSerializing] 共用
{
    keyList = new List<K>(dictionary.Keys);
    valueList = new List<V>(dictionary.Values);
}
public void OnAfterDeserialize()         // Unity 与 [OnDeserialized] 共用
{
    dictionary = new Dictionary<K, V>();
    for (int i = 0; i < keyList.Count; i++)
        dictionary.Add(keyList[i], valueList[i]);
}
```

思路：字段只暴露 `List<K>`/`List<V>`（Unity 与 JsonUtility 都认），真正的 `Dictionary` 标记 `[NonSerialized]`；`ISerializationCallbackReceiver` 服务 Unity 序列化，`[OnSerializing]/[OnDeserialized]` 服务 `BinaryFormatter`，两条通道复用同一对转换函数。实际使用者是输入模块的 `KeyDatas.keyDataDic`。

### 3. `Serialized_Vector` / `Serialized_Color`：值类型降级为纯 float 字段

三者都是 `struct` + `public float x,y,z(,w)`，并提供双向 `implicit operator`（`Serialized_Vector3` 额外支持 `Vector3Int`/`Vector2Int`），另有 `ConverToVector3`、`ConverToSerializationColor` 等扩展方法兜底。意图是把 Unity 类型压成「只有公共 float 字段」的结构，使两个通道输出一致。⚠ 待确认：`Vector3`/`Color` 本身已是 `[Serializable]`，代码未注明为何再包一层，动机无法从源码确认。

### 4. 存储布局：槽目录 + 块文件 + 一份索引

```
persistentDataPath/
├── SaveData/
│   ├── SaveSystemData            ← saveSystemData（槽列表/时间戳/测试槽）
│   ├── 0/PlayerData  InventoryData …
│   └── 1/…
└── Setting/AudioSetting  KeySetting …
```

存档槽彼此隔离（删槽即递归删目录），设置则全局共享一份、不参与槽的生命周期。`GetSavePath(id, createDir)` 兼任「槽是否存在」的校验。

### 5. 三层内存缓存

`cacheDic`（`saveID → fileName → GameDataContainer`）、`settingDataDic`（`Type → SettingDataContainer`）、`dataManagerDic`（`Type → DataManager`，惰性 `new`）。`DataManager` 首次 `GetDataManager<M>()` 时自动实例化，重复显式创建会抛异常。

### 6. `DateTime` 的落盘技巧

`DateTime` 在 JSON 通道不可靠，`SaveItem` 便额外存 `lastSaveTimeString`（`[SerializeField] private`），getter 在 `lastSaveTime == default` 时用 `DateTime.TryParse` 懒还原；二进制通道下该字段属冗余。

## 对外 API 与扩展点

| 场景 | API |
| --- | --- |
| 建槽/删槽/列举 | `CreateSaveItem(int)`、`DeleteSaveItem(int)`、`DeleteAllSaveItem()`、`GetSaveItem(int)`、`GetAllSaveItems()`、`GetAllSaveItemByUpdateTime()` |
| 读写数据块 | `SaveObject<T>(T, int saveID = 0)`、`LoadObject<T>(int saveID, bool ifUseCache = true)`、`DeleteObject<T>(int saveID)` |
| 设置读写 | `LoadSetting<T>()`、`SaveSetting<T>(T)`、`DeleteSetting<T>()`、`DeleteAllSetting()` |
| 业务封装 | `SaveSystem.GetDataManager<PlayerDataManager>()`、`CreateArchive`、`LoadArchive`、`SaveGameDataIntoArchive`、`CreateArchiveForTest()`（仅编辑器） |
| 缓存 | `CleanCache()`（清数据块缓存） |

新增一块要保存的数据，最小示例：

```csharp
[Serializable]
public class PlayerData : GameDataContainer<PlayerData>
{
    public int level;
    protected override void Initialize(params object[] initParams) { level = 1; }
}

SaveSystem.CreateSaveItem(0);                 // 首次保存前必须先建槽，否则 SaveObject 抛异常
SaveSystem.SaveObject(new PlayerData(), 0);   // 文件名 = 类型名 "PlayerData"
var d = SaveSystem.LoadObject<PlayerData>(0);
```

若想挂事件并顺带管设置，继承 `DataManager<PlayerData, AudioSetting>` 后用 `GetDataManager<…>()` 取实例；注意 `GetDataManager<M>` 要求 `new()` 约束，子类必须有公共无参构造。**加解密与版本迁移均未提供**，需要自行在 `IOTool` 或 `SaveFile`/`LoadFile` 前后插入。

## 与其他模块的耦合

- **MyFrameRoot**：`InitSystems()` 首位调用 `SaveSystem.Init()`；`SaveSystem` 反向通过 `MyFrameRoot.Setting.SaveSystemType` 读配置，构成双向依赖。⚠ 待确认：`SaveSystem` 在 `#if UNITY_EDITOR` 下另有静态构造函数调用 `Init()`，进入 Play 时会与 `MyFrameRoot` 的显式调用重复一次（`InitSaveSystemData` 读盘两遍），是否刻意如此源码未说明。
- **Odin Inspector**：本模块 **8 个文件零 Sirenix 引用**。Odin 只出现在 `MyFrameSetting`（`[OdinSerialize] Dictionary`）等处；存档系统走 Unity 原生 `[SerializeField]` + `BinaryFormatter`/`JsonUtility`，与「框架大量使用 Odin」的整体印象不同，需在文档中说明。
- **Editor 工具**：`FrameWindow` 用 `Enum.Parse<SaveSystemType>` 写配置，运行时只读。
- **输入模块**：`Input/KeyData.cs` 的 `KeyDatas` 使用 `Serialized_Dic<string, KeyData>`，包装类型被跨模块复用。
- **命名空间陷阱**：`Serialized_Dic`/`Serialized_Vector`/`Serialized_Color` 三个文件**没有 `namespace`**（全局命名空间），其余五个在 `MyFrame` 下。
- 无协程、无线程、无 async：读写一律主线程同步文件 IO。

## 设计亮点与可改进点

**亮点**

1. 目录即槽位、块即文件：删档即删目录，数据块可独立读写，天然支持局部加载。
2. 索引与数据分离：`SaveSystemData` 独立成文件，列表页不必逐个读存档文件。
3. 双通道可切换：`Binary` 便于保真、`Json` 便于人工查看调试，接口层完全无感。
4. 泛型容器 + 静态门面 + 惰性 `DataManager`，业务接入只需继承两个容器基类。
5. `Serialized_Dic` 一份实现同时满足 Unity 序列化与 `BinaryFormatter`。

**可改进点**

1. **缓存只写不读**：`LoadObject` 命中磁盘后不回填 `cacheDic`，缓存仅在「本次会话保存过该块」时生效，读路径实际一直在读盘。
2. **无安全与健壮性**：无加密、无哈希校验、无 `temp + rename` 原子写、无备份；`IOTool.LoadFile` 只捕获 `SerializationException`，`LoadJson` 连 try/catch 与空文件检查都没有，写一半断电即坏档。
3. **无版本号/迁移**：Binary 通道依赖类型全名，改类名或字段会静默读成 `null`；Json 通道静默取默认值。
4. **每次 `SaveObject` 都整份重写 `SaveSystemData`**，且无脏标记、批量保存或自动存档定时器，保存时机完全由业务手动触发。
5. **死代码与不一致**：`SaveSystemData.currID`、`DataManager<G,S>.TestGameData` 从未使用；事件注销命名 `UnRegisterOnGameDataSave`/`RemoveOnGameDataLoaded`/`RemoveOnGameDataCreated` 三套混用；`SettingDataContainer.Initialize()` 是抽象方法但框架从不调用（`DataManager.Initialize` 用 `?? new S()` 直接构造）。
6. **潜在空引用**：`Serialized_Dic.OnAfterDeserialize` 未判空 `keyList`，反序列化出空对象时会 NRE；`DeleteObject` 中 `GetSavePath(false)` 可能返回 null 却继续拼路径。
7. **转换小瑕疵**：`Serialized_Vector2 → Vector2` 的隐式运算符内部 `new Vector3(...)`（靠 Unity 隐式转换绕过，语义对但不直观）；`ConverToSVector2(this Serialized_Vector2)` 名为转 SVector2 实际返回 `Vector2`。
8. `BinaryFormatter` 已被现代 .NET 标记为不安全/弃用，长期建议改用 JSON 或自研二进制格式。
