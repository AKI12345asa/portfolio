## 从行为树到 GOAP

行为树的隐含前提是，在某个状态下 AI 一定会执行某件事。整棵树因此是在预先枚举所有可能性：状态组合有多少，分支就有多少。一旦 AI 要同时考虑血量、距离、队友位置、技能冷却，分支会爆炸，改一根枝还可能影响另一根。

GOAP 换了一种建模方式。它不问这个状态该走哪条分支，只维护两样东西：当前是什么状态，以及有哪些能改变状态的行动。AI 因此不依附于某条具体逻辑链。血量、距离、有没有进入攻击距离，都由业务侧每帧写进状态表；每个行动自己声明优先级（值不值得做）和效果（做完能得到什么），规划器按优先级挑；新增一个行动不必改任何已有行动，也不必把它插进某棵树，只是多了一个可选手段。

复杂分支的开发难度因此从几何增长变成线性增加：加一个行为等于加一个类加一条配置。

## 三个核心抽象

状态是一张世界状态表，值是 `Bool / Float / Int / UnityObject` 四种。业务侧通过 `IGOAPOwner` 每帧把真实数据写进来，框架不认识你的角色，只认识这张表。

比较器同时承担三件事：表达前提（我要血量大于 50）、表达效果（我会把血量提高 20），以及把效果应用到状态上。一物三用，配置量因此很小。

行动声明前提、效果、优先级、代价与执行体。执行体返回 `Running / Success / Failed`，失败就丢弃整个计划重新规划。

## 规划器：启发式引导的回归分解

规划器没有采用 A\*，这是刻意的选择。

### 计划结构是 AND/OR 树

A\* 能成立的前提是每个节点只需选一个后继（OR 关系），所有候选因此可以放进一个 open 集按 `f` 全局比较。GOAP 的计划结构是 AND/OR 树：

```
目标「击败敌人」
 └─ 动作「攻击」          (AND：所有前置必须同时成立)
     ├─ 前置「在攻击距离内」 (OR：任意一个动作做到就行)
     └─ 前置「武器已拔出」   (OR：任意一个动作做到就行)
```

给「在攻击距离内」找解和给「武器已拔出」找解是两件并列的事，不存在二选一的关系，也就没法放进同一个 open 集按 `f` 比较。

要在 GOAP 上硬套 A\*，必须先把 AND/OR 展平成世界状态图（节点是状态快照，边是动作），这才需要状态拷贝和哈希，浮点还得量化，换来的是总代价最优。

在动作游戏里，这个最优的价值很低。计划寿命极短，世界状态每帧都在变，最优解往往还没执行完就失效；决策是高频调用，要的是一帧内出结果；行为还要可解释，设计师得看得懂 AI 为什么这么做，回归分解天然能解释，`f` 值讲不清楚。

所以这里选择的是递归分解、启发式排序与失败回溯。

### 规划流程

```
① 求差：目标的期望值 vs 当前状态 → 得到未满足的条件集合
② 从优先级最高的条件开始
③ 找候选：所有"有某个效果能匹配这个条件"的行动
④ 排序：f = 行动代价 + h
       h = 该行动所有未满足前置的「最便宜满足代价」之和
⑤ 递归：对选中的候选，为它的每条未满足前置再走一遍 ②~⑤
       任一前置无解 → 换下一个候选（这就是回溯）
⑥ 收敛：所有前置都有解 → 节点"完整"，挂到父节点上
       深度超过上限 → 判失败
```

第 ④ 步的 `h` 是从当前这个行动往后还要花多少代价，不含这个行动本身的代价，那部分已经在 `g` 里。

### 乐观匹配的语义

AI 的行为效果大多是模糊的：加血、加速、拉近距离，很少产生精确等于某个值的结果。所以效果匹配用的是乐观语义，只要这个行动有可能让条件成立，就算匹配。

具体规则在 `FloatState.MatchWithComparer` 里：绝对值直接比大小，增量只看符号方向。效果是「提升 HP 20」、要求是「HP > 50」时算匹配，因为它会往对的方向走；效果是「HP 设为 30」这种绝对赋值、要求同为「HP > 50」时不算匹配，30 到不了 50。

这是刻意的取舍：规划的是当下有哪些合理手段，数学上并不保证达成。代价是执行期可能发现效果不足，`CheckForEffect` 失败后重规划。用可能达成换配置简单与行为自然。

### 从 A\* 保留的两点

| 保留 | 作用 |
| --- | --- |
| 启发式 `h` | 把"先试哪个动作"从"配置顺序"变成"代价小的优先"——**这是行为合理性的关键** |
| `f = g + h` 的分量 | `g` 是父链上已选动作的代价，`h` 是从这里往后还要多少，两者共同决定尝试顺序 |

丢掉的是全局 open/closed 集和最优性保证。在 AND/OR 结构里，这两样东西本来就没有意义。

### 代价与回收

规划节点是池化的。一次规划会创建几十个候选节点，失败候选要整体回滚，连同它已经建立的子树一起清掉。所以每个节点记录 `Parent` 与 `Preconditions`，回收时沿子树递归清理，避免失败的候选把正在用的分支一起销毁。

## 执行

规划结果是一棵先子后父的执行树：要做 A 之前得先做 B，那就先跑 B。每个节点每帧被 Tick 一次，返回 `Success` 才轮到下一个。

任何节点返回 `Failed`，整个计划作废，重新回到目标选择。行动的 `CheckForEffect` 写得越保守，重规划越少。

## 读图要点

框架里没有感知层。世界状态由 `IGOAPOwner`（业务侧）每帧从真实对象读出来写回，框架只负责用状态做决策。这是不侵入业务的代价，也是它能复用到任何 AI 上的原因。

字段到状态的绑定在初始化阶段用 Expression 编译成委托，运行期每帧只做一次委托调用，不走反射。

目标选择按优先级取第一个可满足的，不做多目标联合优化，所以「AI 想做什么」始终可预测、可调试。

规划失败是常规路径，不是异常。某个前置没有任何行动能满足时，规划干净地返回失败，交给下一轮重新选目标。

## 核心类型

| 类型 | 职责 |
| --- | --- |
| `GOAPAgent` | 主循环：感知 → 选目标 → 规划 → 执行 → 重规划 |
| `GOAPActionBase` | 行动基类：前提、效果、代价、优先级、执行体 |
| `GOAPStateBase` | 状态基类，派生 Bool / Float / Int / UnityObject |
| `GOAPStateComparer` | 比较器：前提判定 / 效果判定 / 效果应用 |
| `GOAPPlanNode` | 规划节点：`G`/`H`、`Parent`、`Preconditions`、`Pending` |
| `GOAPPlan` | 执行器：找最深节点、按优先级推进、完成/失败回收 |
| `GOAPUtility` | Expression 绑定编译 |

## 扩展方式

- 加一个行动：继承 `GOAPActionBase`，标 `[GOAPAction("名字")]`，写好前提、效果、优先级与 `StartRun` 的返回状态。
- 加一个目标：继承 `Goals`，声明目标状态与优先级。
- 给前置排优先级：`GOAPTypeAndComparer.Priority` 决定同一个行动的多条前置谁先被规划、先被执行。
